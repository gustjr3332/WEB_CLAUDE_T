# Google Apps Script 배포 방법

구글 계정 인증이 필요한 단계이므로 아래 과정은 직접 진행해 주세요.

1. 스프레드시트 열기: https://docs.google.com/spreadsheets/d/1MOCGapRs-sc1civpI3wwV0BsYm85gMSTKsHoZOVmHJA
   (`gustjr3332@gmail.com` 계정으로 접근 권한이 있어야 합니다.)
2. 메뉴에서 **확장 프로그램 → Apps Script** 클릭.
3. 기본으로 생성된 `Code.gs` 내용을 전부 지우고, 이 폴더의 `Code.gs` 내용을 붙여넣기.
4. 상단 **배포 → 새 배포** 클릭.
   - 유형: **웹 앱**
   - 다음 사용자 권한으로 실행: **나(본인 계정)**
   - 액세스 권한이 있는 사용자: **모든 사용자** (익명 클라이언트에서 POST 요청을 보내야 하므로 필요)
5. 배포 후 발급되는 **웹 앱 URL**(`https://script.google.com/macros/s/xxxx/exec` 형태)을 복사.
6. 프로젝트 루트의 `config.js` 파일을 열어 `APPS_SCRIPT_URL` 값을 방금 복사한 URL로 교체.
7. 처음 배포 시 구글이 권한 승인(스프레드시트 접근 등)을 요청합니다. 승인해야 정상 동작합니다.

## 8. 1분마다 자동 집계 트리거 등록 (★ 반드시 필요, 한 번만 하면 됨)

브라우저가 열려 있지 않아도 서버(Google) 쪽에서 알아서 집계가 돌아가게 하려면
시간 기반 트리거를 등록해야 합니다.

1. Apps Script 편집기 상단의 함수 선택 드롭다운에서 **`createTrigger`** 선택.
2. **실행(▶)** 버튼 클릭.
3. 처음 실행 시 권한 승인 팝업이 뜨면 승인.
4. 왼쪽 메뉴의 시계 아이콘(트리거)을 클릭하면 `aggregateAndClearPending` 함수가
   "시간 기반 / 분 타이머 / 1분마다"로 등록된 것을 확인할 수 있습니다.

이후부터는 브라우저를 아무도 켜놓지 않아도 1분마다 Google 서버가 알아서
`Pending`을 읽어 `LIKE`에 합산하고, 영향받은 날짜의 `일별 좋아요 집계`를 다시 계산한 뒤
`Pending`을 비웁니다.

## 시트 구조

시트 탭 3개, 각각 속성 중복 없는 단일 테이블입니다.

| 시트 | 컬럼 | 의미 |
|---|---|---|
| `LIKE` | Date, Hour, PostID, PostTitle, LikeCount, LastUpdated | 정규화된 원본 데이터. 날짜+시간+포스트 단위로 딱 한 행만 존재하는 "단일 진실 공급원(source of truth)" |
| `Pending` | ServerTimestamp, PostID, PostTitle | 클릭 원시 로그. 내부 처리용 큐라서 필요하면 탭을 숨겨도 됨. 트리거가 처리 후 자동으로 비움 |
| `일별 좋아요 집계` | 날짜, 오늘의 총 좋아요 수, 최다 좋아요 포스트 | 대시보드용 요약. 값을 누적하지 않고, 매번 `LIKE` 테이블을 다시 훑어 계산한 결과로 덮어씀 (그래서 항상 정확함) |

`LIKE` 시트에는 이제 표가 하나뿐이라 PostID/PostTitle/LikeCount 같은 속성이 중복 등장하지 않습니다.
포스트별 전체 순위 같은 다른 관점이 필요해지면, 이 정규화된 `LIKE` 테이블을 원본으로 삼아
`QUERY`/`SUMIFS` 같은 시트 함수로 얼마든지 새로 뽑아낼 수 있습니다.

### ★ 기존 데이터 마이그레이션 (한 번만 실행)

이전 버전에서는 `LIKE` 시트 하나에 Post/Hourly/Daily/Pending을 열 블록으로 욱여넣어 사용했습니다.
이미 쌓인 데이터를 잃지 않고 새 구조로 옮기려면:

1. Apps Script 편집기 상단의 함수 선택 드롭다운에서 **`migrateToNormalizedSheets`** 선택.
2. **실행(▶)** 클릭. (처음이면 권한 승인 팝업 승인)
3. 실행 로그(보기 → 실행 기록)에 "마이그레이션 완료: LIKE N행 이전, 일별 집계 M일 계산됨." 이 보이면 성공.

이 함수는 기존 Hourly 블록(F:K열) 데이터를 읽어 새 `LIKE` 시트로 옮기고, `Pending`/`일별 좋아요 집계`
시트를 새로 만든 뒤 지금까지의 날짜별 요약을 계산해 채웁니다. **딱 한 번만 실행하세요** — 다시 실행하면
그 시점의 `LIKE` 블록 레이아웃을 다시 읽으려 시도하므로, 이미 정규화된 상태에서 또 실행하면 안 됩니다.

### ★ 날짜 비교 버그 복구 (한 번만 실행)

Google Sheets가 `"2026-08-23"` 같은 날짜 문자열을 셀에 쓰는 순간 자동으로 진짜 Date 값으로
바꿔버리는 경우가 있습니다. 이 때문에 스크립트의 문자열 비교가 항상 실패해서, `일별 좋아요 집계`가
0으로만 나오고 `LIKE` 시트도 합산되지 않고 (같은 날짜/시간/포스트인데도) 매번 새 행으로 계속
쌓이는 문제가 있었습니다. 최신 `Code.gs`는 이 비교를 고쳤고 날짜 컬럼을 텍스트 서식으로 고정해
앞으로는 재발하지 않지만, **이미 쌓인 데이터**는 한 번 정리해줘야 합니다.

1. Apps Script 편집기 상단의 함수 선택 드롭다운에서 **`repairDuplicateLikeRows`** 선택.
2. **실행(▶)** 클릭.
3. 실행 로그에 "복구 완료: LIKE N행으로 정리(합산), 일별 집계 M일 재계산됨." 이 보이면 성공.

이 함수는 `LIKE` 시트의 모든 행을 다시 훑어 같은 (날짜, 시간, 포스트)를 하나로 합치고, 날짜를
텍스트로 통일해서 다시 쓴 뒤 `일별 좋아요 집계`도 전부 재계산합니다. (`migrateToNormalizedSheets`와
달리 이건 여러 번 실행해도 안전합니다 — 매번 다시 합쳐서 같은 결과가 나옵니다.)

## 동작 확인
- 브라우저에서 웹 앱 URL을 그냥 열어보면(`GET` 요청) `{"status":"ok", ...}` 응답이 보이면 배포가 정상입니다.
- 블로그 페이지에서 LIKE 버튼을 누르면 클릭 즉시 `Pending` 시트에 한 줄이 추가됩니다 (탭을 바로 닫아도 무관).
- 최대 1분 안에 트리거가 실행되어 `Pending` 데이터가 `LIKE`로 합산되고, `일별 좋아요 집계`의 해당 날짜
  행이 갱신되고, `Pending`은 비워집니다.

## 코드를 수정한 경우
- `Code.gs` 내용을 바꿨다면 **배포 → 배포 관리 → 수정(연필 아이콘) → 새 버전으로 배포** 를 눌러야 웹 앱 URL(doPost/doGet)에 변경사항이 반영됩니다. (URL 자체는 바뀌지 않습니다.)
- `aggregateAndClearPending` 함수의 로직만 바꾼 경우에는 재배포 없이도 다음 트리거 실행부터 바로 반영됩니다. (트리거는 웹 앱 배포와 별개로, 항상 최신 코드로 실행됩니다.)
- 이미 `createTrigger`를 한 번 실행해서 트리거가 등록되어 있다면, 이번 구조 변경 때문에 다시 실행할 필요는 없습니다(함수 이름이 그대로라 기존 트리거가 새 코드를 그대로 사용합니다).
